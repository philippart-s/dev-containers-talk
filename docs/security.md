# 🔒 Dev Containers and security

Answers to the questions asked during the talk, and the settings shown in `step-12`.

## Questions

### Does the container run as root?

It depends on two settings:

- `remoteUser`: the user VS Code connects with (terminal, extensions). The `mcr.microsoft.com/devcontainers/*` images set it to `vscode` (UID 1000).
- `containerUser`: the user of the container process itself (PID 1). When the image does not set it, it is `root`.

Without `step-12`, the terminal runs as `vscode` but PID 1 runs as `root`, and `vscode` has `sudo` without a password (inherited from the base image). In practice, any code running as `vscode` can become root in the container.

### Is root in the container root on my Mac?

No. On macOS, containers run inside a Linux VM (Rancher Desktop: Lima with Apple Virtualization). Root in a container is at most root in that VM.

What the container can reach on the Mac is what is mounted: the workspace is bind-mounted read-write, so code running in the container can modify the project files.

### What about Docker in Docker and Docker outside of Docker?

- Docker in Docker needs `--privileged`: all capabilities and access to the VM devices, the isolation stops at the VM level.
- Docker outside of Docker mounts the engine socket: the container drives the VM's Docker engine and can start privileged containers, which is an equivalent level of power.

Both are build tools. In this repository only `step-10` uses one (Docker outside of Docker, to reuse the build cache), the final image does not contain any.

### Is opening someone else's repository in a dev container risky?

As risky as running `mvn install` or `npm install` on it: `postCreateCommand`, features and Dockerfiles run code. VS Code asks for Workspace Trust before opening a folder in a container.

By default, VS Code also shares with the container the host git configuration (`dev.containers.copyGitConfig`), git credentials and the SSH agent when one is running. A malicious repository can use them, for instance to push with your SSH key.

### Are features a supply chain risk?

Yes. A feature is an OCI artifact whose `install.sh` runs as root at build time, and `ghcr.io/devcontainers/features/java:1` means "the latest 1.x at build time". Mitigations:

- features from trusted publishers, with an explicit version,
- `devcontainer-lock.json`: generated by the dev container CLI and VS Code, it pins the version and digest of each feature and is meant to be committed with the code (this demo repository ignores it to keep the steps readable); `devcontainer upgrade` updates it,
- an internal image built once and pushed to a private registry (`step-10`), so that projects only pull it.

### What does Rancher Desktop without admin access change?

The Docker engine runs as root inside the VM, not on macOS. With `adminAccess: false`, Rancher Desktop does not create `/var/run/docker.sock` on the Mac and needs no macOS privileges; the engine is reached through `~/.rd/docker.sock` (`docker context use rancher-desktop`).

## Settings shown in step-12

```jsonc
"image": "…/devcontainer-base-image-talk:1.6.1@sha256:414a5d99…",
"containerUser": "vscode",
"securityOpt": ["no-new-privileges"],
"runArgs": ["--cap-drop=ALL"]
```

| Setting | Effect | Trade-off |
|---|---|---|
| image digest | a tag moved on the registry does not change the environment | the digest is updated by hand for each new image |
| `containerUser` | PID 1 runs as `vscode` | none observed with this image |
| `no-new-privileges` | `sudo` and setuid binaries cannot raise privileges | no `sudo apt install` in the container: missing tools go in a feature or in the image |
| `--cap-drop=ALL` | the 14 capabilities Docker grants by default are removed | tools that need a capability must add it back with `capAdd` |

Not covered: the workspace stays writable, by design.

## Registry: OVHcloud Managed Private Registry (Harbor)

In the Harbor UI, project `library`:

1. **Vulnerability scanning** — *Configuration* tab: check *Automatically scan images on push*, then scan the existing artifacts once (*Repositories* → select → *Scan vulnerability*). Optionally, *Prevent vulnerable images from running* with a severity threshold blocks pulls above it.
2. **Immutable tags** — *Policy* tab → *Tag Immutability* → *Add rule*: repositories matching `**`, tags matching `**`. A published tag can then neither be overwritten nor deleted, fixes go to a new tag (`1.2.1`, `1.6.1`).

Delete the tags you no longer need (`1.2.0`, `1.6.0`) before adding the immutability rule: immutable tags cannot be deleted.
